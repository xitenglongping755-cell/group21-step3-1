# GitHub 運用ルール(3人チーム用)

3人でGitHubを使って作業するための最低限のルールをまとめたものです。
方針はシンプルな **GitHub Flow**(作業ブランチ + プルリクエスト + レビュー + マージ)を採用します。

## 1. 最低限決めるべきルール一覧

| 分類 | 決めること | 3人チームのおすすめ例 |
|---|---|---|
| ブランチ運用 | `main` への直pushを禁止し、作業は必ずブランチで行う | GitHub Flow:`main` から `feature/説明` を切る |
| ブランチ名 | 命名規則を統一 | `feature/課題番号-短い説明`(例:`feature/12-add-login`) |
| PR・レビュー | 全変更をPR経由にし、承認人数を決める | レビュー承認1人でマージ可。ただし**自己マージ(自分のPRをレビューなしでマージ)は禁止** |
| マージ方法 | squash / merge / rebase のどれかを統一 | **squashマージ**(履歴がPR単位できれい)。マージ後にブランチを削除 |
| コミットメッセージ | 形式と言語を統一 | Conventional Commits(`feat:` `fix:` `docs:` など)+日本語で概要 |
| Issue運用 | どんな作業をIssueに上げるか、PRとの紐付け方 | 作業前に必ずIssueを作成、PRの説明欄に `fixes #12` と書いて自動で紐付け・クローズ |
| リポジトリ設定 | `main` の保護設定を入れる | Settings → Branches → Branch protection で「PR必須」「承認1人必須」「直push拒否」を有効化 |
| 禁止事項 | コミットしてはいけないものを明記 | APIキー・パスワードなどの秘密情報、`.env`、ビルド生成物は `.gitignore` で除外 |

## 2. ブランチ運用の詳細

- `main` は常に動く(デプロイ可能な)状態を保つ
- 作業を始める前に `main` から作業ブランチを切る

```bash
git checkout main
git pull origin main
git checkout -b feature/12-add-login
```

- ブランチ名のプレフィックス例:
  - `feature/` … 新機能の追加
  - `fix/` … バグ修正
  - `docs/` … ドキュメントのみの変更
  - `chore/` … その他雑務(設定変更など)

## 3. プルリクエスト(Pull Request)のルール

- どんな変更も必ずPR経由で行う(`main` への直接pushは禁止)
- PRの説明欄には「何を・なぜ変更したか」を書く
- 対応するIssueがある場合は `fixes #12` のように紐付けて、マージ時に自動クローズする
- **自分のPRを自分でレビューなしにマージしない(自己マージ禁止)**
- レビューは原則として1営業日以内に返す
- 大きな変更になりそうな場合は、実装前に事前にチームで相談する

## 4. コミットメッセージのルール

Conventional Commits の形式 + 日本語で概要を書く:

```
feat: ログイン機能を追加
fix: 一覧画面のページネーションを修正
docs: セットアップ手順を追記
```

- `feat:` … 新機能
- `fix:` … バグ修正
- `docs:` … ドキュメント
- `chore:` … ビルド・設定などの雑務

## 5. リポジトリ設定(保護ルール)

Settings → Branches → Branch protection rules で `main` に対して:

- [ ] プルリクエスト必須(直接pushを拒否)
- [ ] 承認(Approve)1人必須
- [ ] マージ後のブランチ自動削除

ルールは人の運用任せにせず、**GitHub側の設定で強制**するのが最も確実です。

## 6. 禁止事項

以下は絶対にコミットしない:

- APIキー・パスワード・トークンなどの秘密情報
- `.env` などの環境設定ファイル(`.gitignore` に登録)
- ビルド生成物・一時ファイル

誤ってpushしてしまった場合は、すぐにチームへ連絡すること(キーの無効化などが必要)。

## 7. 日々の作業の流れ(まとめ)

1. 作りたい内容をIssueに上げる(または既存Issueを確認)
2. `main` から作業ブランチを切る(`feature/12-add-login` など)
3. コミットメッセージのルールに従ってコミットし、pushする
4. PRを作成し、レビューを依頼する
5. レビューで承認をもらったら squashマージ
6. マージ済みブランチを削除して次の作業へ

---

*このルールに不足や変更が必要だと思ったら、気軽にIssueを立てて提案してください。*
